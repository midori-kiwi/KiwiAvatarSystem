5. B10 EXACT SOURCE-ROTATION CONTRACT
============================================================

[Source Producers]
- Native-active WindowsNativeWebCamSource overrides rotation=Rotation0 and publishes the
  provider-normalized KiwiNativeCameraPresentation texture. Domain={0}.
- When not native-active, the override delegates to WebCamSource.rotation.
- WebCamSource.rotation returns (RotationAngle)webCamTexture.videoRotationAngle after prepare.
- Unity 6000.0 public API documents videoRotationAngle as the camera-content clockwise angle
  used to orient the image correctly:
  https://docs.unity3d.com/6000.0/Documentation/ScriptReference/WebCamTexture-videoRotationAngle.html
- Installed ImageTransformationOptions tests exercise Rotation0/90/180/270. Current fallback
  source has no Windows-specific rejection, normalization-to-zero, or accepted-domain guard for
  the nonzero values.

[MediaPipe Consumer]
- ImageSource.GetTransformationOptions returns flips plus source rotation.
- Runner initialization constructs ImageProcessingOptions(rotationDegrees=(int)rotationAngle).
- On an owned source identity/name/dimension refresh, Runner reconstructs the same options from
  the refreshed source.
- Installed BaseVisionTaskApi requires a multiple of 90, writes normalizedRect.Rotation=
  -rotationDegrees*pi/180, and swaps rect width/height for 90/270.
- MediaPipe therefore consumes the nonzero source-rotation contract.

[IE Consumer]
- InitializeSentisTracker accepts only source Texture, flipHorizontally, flipVertically.
- Refresh stores only _sentisSourceTexture and those two flip booleans.
- KiwiInferenceFaceTracker.TryProcess/TryProcessAsync/ScheduleModel likewise accept no source
  rotation value.
- ScheduleModel computes samplingMatrix=BuildFlipMatrix(h,v)*cropMatrix and sends it to the
  crop shader. BuildFlipMatrix contains only x->1-x and/or y->1-y reflections.
- KiwiInferenceFaceCrop.shader samples mul(_Xform,(cropUv,0,1)).xy. No source-rotation matrix,
  90/270 dimension swap, rotationAngle, or rotationDegrees is present.
- DecodeReadableOutput projects using the unrotated same-lane cropMatrix. ROI roll is a separate
  face-ROI transform and is not a substitute for source-image rotation.

[Rotation-Only Equation / Counterexample]
- Let P be an arbitrary physical source feature and let F be the already separate flip/origin
  preprocessing transform. For the rotation subclaim, factor F as common input processing and
  vary only source rotation r.
- MediaPipe model-input coordinate: M_input(P)=R_r(F(P)), with the installed 90/270 dimension
  handling where applicable.
- IE model-input coordinate: I_input(P)=F(P), followed by the existing ROI crop; there is no R_r.
- For native-active r=0, R_0 is identity and this B10 subclaim passes.
- For fallback r in {90,180,270}, choose any asymmetric P not fixed by R_r. Then
  R_r(F(P)) != F(P). The model pixels and source-normalized semantics cannot be generally equal.
- This counterexample does not rely on horizontal mirror, vertical-origin equivalence, preview
  display state, model numerical equality, or Runtime frequency.

[First Conflict]
- Producer=WindowsNativeWebCamSource fallback -> WebCamSource.rotation ->
  WebCamTexture.videoRotationAngle.
- Accepted nonzero domain=Rotation90/Rotation180/Rotation270 in the current transform/API path.
- MediaPipe consumer=Runner ImageProcessingOptions.rotationDegrees -> installed
  BaseVisionTaskApi normalizedRect rotation and 90/270 dimension swap.
- Missing IE boundary=Runner InitializeSentisTracker/current refresh and
  KiwiInferenceFaceTracker.ScheduleModel have no source rotation or equivalent transform.
- Exact defect=SOURCE_IMAGE_ROTATION_NOT_CARRIED_TO_IE_CROP.

[B10 Decision]
- B10_WINDOWS_NATIVE_ACTIVE_SUBDOMAIN=PASS with MEDIAPIPE_SOURCE_ROTATION=0 and
  IE_SOURCE_ROTATION=0 only while native remains active.
- B10_WINDOWS_NATIVE_PRODUCTION=FAIL because the complete Production-reachable fallback domain
  admits nonzero rotation to MediaPipe while IE remains source-rotation 0.
- Physical upright orientation and sensor correctness are not claimed.
- Generic nonzero rotation is not classified as mobile/P20 and is not deferred outside the
